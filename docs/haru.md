# Haru-4B on the Mac (duplex trial, `haru-4b`)

**What:** `higurashi-ai/Haru-4B`, a full-duplex spoken-dialogue *base* model from higurashi (Tokyo): it listens and
speaks at once, one 133 ms frame at a time, audio and text in every frame. Qwen3.5-4B backbone (32 layers, hidden
2560; 5B parameters in bf16), VibeVoice codec at 24 kHz, a MeanFlow one-step audio head. English is one of nine
languages; **no Danish**. Official MLX package `haru_mlx` (PyPI `haru-speech-mlx`) and a macOS app.

**Licence (read 2026-11-27):** Apache-2.0 for the code and the weights (model card front matter `license:
apache-2.0`; README "The code and the Haru-4B weights are released under the Apache License 2.0"; `haru_mlx`'s
pyproject names `LICENSE` and `THIRD_PARTY_NOTICES.md`). Keep the notices with anything we ship from it. Its README:
*only use voices you have the right to use* — mux's clip is Kokoro's af_heart (Apache-2.0), generated by mux.

**What it is not:** an assistant. The card calls it a pretrained base model, "not a reliable source of facts"; the
authors say the small backbone limits response quality. **No tool use.** So it is a trial of what full duplex
*feels* like on our Mac, and Bloom's voice front only if forced text works (below).

## On mux

- `./deploy/haru.sh`: `~/.mux/haru-venv` with `haru-speech-mlx==0.1.0` (or the repo's `haru_mlx` from git), the
  weights (~10 GB), the voice clip `~/.mux/haru/voice-en.wav` (Kokoro af_heart through the speak route, ~25 s), the
  server `server/realtime/haru_server.py` as `com.mux.haru` on 127.0.0.1:8321 (8-bit by default; `--bf16`), the
  model `haru-4b` (kind `realtime`, `base_url` http://127.0.0.1:8321/v1) on the route `realtime`.
- haru_mlx has no network server (only its app's Unix socket and offline inference), so `haru_server.py` is the
  wrapper: mux's engine protocol on `/duplex` (docs/realtime.md), one conversation at a time, every MLX call on
  haru_mlx's `MLXWorker` thread (MLX keeps GPU streams per thread). Caller audio is resampled 16 → 24 kHz and fed as
  it arrives (`feed()`); a model frame goes back for every user frame (`step()`), silence included.
- **Memory floor:** `GET /v1/models` says `need_gb` 12 until loaded; mux makes room or refuses (503 `memory_busy`).
  The model loads on the first session; after 15 idle minutes the process exits and launchd starts it unloaded.
- A session: `{"type":"session.start","model":"haru-4b","instructions":"…"}`. No tools. `input.text` is not heard.

## The forced-text experiment (the deciding test)

Haru's public session API cannot be steered mid-call (`start()` and `step()`; `speak_first` only bans the silent
tokens for one frame — it does not choose words; read in `haru_mlx/session.py`). But each frame samples one text
token and the voice follows the text stream. `server/realtime/haru_forced.py` replaces the sampled token with the
next token of a given sentence (after an EOP, the token that starts a turn) by wrapping `sample_token` for that frame;
nothing is patched on disk. In a session, `response.create {"say": "…"}` does this (the hybrid: Bloom's LLM writes,
Haru speaks).

`./deploy/haru.sh --forced-text` runs `server/realtime/haru_forced_text.py`: three sentences, each as *control*
(Haru unforced, same seed), *dense* (a token a frame) and *paced* (a PAD after each token), transcribed through mux's
`transcribe` route, WER against the sentence, and the step time. **PASS** when the better forced mode has WER ≤ 0.25
on every sentence. The control tells a broken setup from a FAIL. Takes in `~/.mux/haru/forced/`.

## Known limits

- Vendor latency: p50 65 ms of processing on an M1 Max int8 plus up to 133 ms of framing; unmeasured on our M3 Ultra
  through mux (the wrapper and the socket add their own).
- The 60-minute conversation limit of `DuplexConfig.max_frames`.
- What was checked here: the wrapper's protocol, the memory floor and the forced-text path, end to end through mux's
  `/v1/realtime`, against a fake `haru_mlx` (no MLX on Linux). Nothing has run against the real model.
